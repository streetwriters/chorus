# Notesnook HA changes

This patch keeps the existing provider registry, Redis switch records, version vectors, and Asynq event queues.

- S3 client construction does not probe providers, so Proxy and Worker can register configured providers while one is offline. A live `HealthChecker.Probe` is used only when a switch needs a source availability decision. The persisted route is loaded from Redis after restart.
- A switch may enter `PROMOTED_WITH_BACKLOG` only after initial source discovery completes, with at least one event still pending and the source unavailable. Reads use the switch record's replication ID even after its policy is archived. A known source-only object is routed to its source; provider network failures return S3 `ServiceUnavailable` / HTTP 503. While promoted, B is active, the switch no longer occupies the active-switch slot, and the blocked repair event remains in Redis/Asynq. The switch reaches `DONE` after repair drains if A returns. New B writes advance the old A→B version vector so delayed source writes and deletes cannot overwrite newer B state. A B→C policy can be added while old repair remains pending.
- Deletes carry explicit durable intent and source mutation versions; workers never infer deletion from missing version metadata or a missing source object. A delayed delete applies only when its exact source version is still current and newer than the target. Legacy versionless delete tasks are applied only when no vector state exists. Mutations on B during an in-progress, promoted, or done switch enqueue reverse repair until a B→A policy exists. Capturing in-progress writes also covers requests that obtained their routing context before switch completion but reach B after recovery replication starts. Recovery policies may be added while the `DONE` switch record remains, closing the former record-deletion handoff gap; keep the switch metadata until recovery replication protection exists. If an object sync event cannot be stored, Proxy returns retryable HTTP 503 instead of silently acknowledging it.
- Multipart uploads under replication are recorded in Redis with their initiating provider so routing remains correct across a switch. Markers, including successful completion receipts, remain until their bounded TTL (seven days for ordinary uploads) or explicit abort. On `NoSuchUpload`, a retry uses HEAD and matches the saved completion ETag, size, and last-modified time before returning idempotent success and re-enqueuing replication. New markers are not reconciled without a durable receipt. A crash after provider completion but before Chorus persists that receipt remains an unavoidable S3/Redis atomicity gap: Chorus fails conservatively rather than mistaking a different object at the key for this upload, so manual resolution may be needed for that narrow case.
- Each upload marker now records its own expiration. The shared user/bucket Redis set TTL is extended atomically to the latest marker deadline and never shortened by concurrent uploads; expired entries are pruned when that bucket's upload state is read or updated. A later upload in the same bucket therefore cannot extend an older completion receipt beyond its original window.
- Single-object Proxy DELETE and Worker object replication share the same destination-scoped Redis object locks. Proxy holds the relevant active, replication-target, and any completed switch's potential reverse-target locks through provider DELETE, vector advancement, and durable replication enqueue. Including that potential destination protects the handoff if B→A recovery policy is installed while the request is in flight. This closes the in-flight stale-copy race in either ordering. `DeleteObjects` batch requests are not serialized by this pass; Notesnook's attachment delete path uses single-object DELETE. Generic PUT/overwrite locking remains out of scope because Notesnook attachment keys are immutable and not reused.
- Query-string SigV4 GET, PUT, and multipart UploadPart are covered by the MinIO integration test. A test-only helper uses the exact AWSSDK.S3 3.7.310.8 package and Notesnook settings (`ServiceURL`, `AuthenticationRegion`, path-style, SigV4, `GetPreSignedURLAsync`).

## Verification and limits

Run Go commands with Go 1.27.1 or newer. The MinIO integration test also needs .NET 8 and the AWSSDK.S3 3.7.310.8 NuGet package; it skips the SDK-specific case when `dotnet` is unavailable. A previous verification pass ran `go test ./test/minio -count=1` successfully with the Notesnook presigned GET, PUT, and UploadPart cases. In the final lock/TTL pass, the focused package set and race-detector regressions passed. The required final MinIO attempt and broad suite could not complete their container-backed packages because Testcontainers reported `rootless Docker not found, failed to create Docker provider`; all `pkg` and `service` packages passed. The generic `docker-compose/docker-compose.yml` is not the dedicated outage lab, and the Docker daemon at `~/.docker/run/docker.sock` was unavailable, so live Proxy/Worker restart and failover scenarios were not rerun.

The live Docker lab verified the blocked-event path: with A offline and a queued A-only object, switch status became `PROMOTED_WITH_BACKLOG`; Proxy and Worker restarted successfully; GET/HEAD of replicated data and new PUTs to B worked; the source-only read returned HTTP 503. The queued event remained pending and copied to B after A returned, moving the switch to `DONE`. A separate live check deleted an object on B during promoted backlog; after A returned and the reverse delete task retried, the stale object was absent from both providers. The management CLI in the lab is older than this patch and renders the new enum as `NOT_STARTED`; query `/replication/switch/get` to see `PROMOTED_WITH_BACKLOG` until `chorctl` is updated.

The version-vector guard covers delayed events after the newer mutation has been recorded. Single-object DELETE now serializes against Worker copies with the shared object lock. Generic PUT/overwrite requests remain outside that lock; this is accepted for Notesnook's immutable, non-reused attachment keys. S3 `DeleteObjects` batches are also not covered by the lock and remain a limitation if consumers use that path.

Asynq object events use a retry cap of `MaxInt32`, which is operationally very large but finite. Permanent provider errors such as `AccessDenied` can therefore remain in retry state; this patch does not add a permanent/transient error classifier or a separate retry subsystem.

Multipart retry recovery depends on the Redis upload marker remaining available and unexpired. Ordinary upload markers expire after seven days; an upload abandoned longer than that may not be eligible for the `NoSuchUpload` reconciliation path. S3 object mutation and Redis enqueue are not atomic for non-multipart requests; Proxy reports queue failure as retryable HTTP 503, but durable replay still depends on the client retrying.
