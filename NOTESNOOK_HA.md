# Notesnook HA changes

This patch keeps the existing provider registry, Redis switch records, version vectors, and Asynq event queues.

- S3 client construction does not probe providers, so Proxy and Worker can register configured providers while one is offline. A live `HealthChecker.Probe` is used only when a switch needs a source availability decision. The persisted route is loaded from Redis after restart.
- A switch may enter `PROMOTED_WITH_BACKLOG` only after initial source discovery completes, with at least one event still pending and the source unavailable. Reads use the switch record's replication ID even after its policy is archived. A known source-only object is routed to its source; provider network failures return S3 `ServiceUnavailable` / HTTP 503. While promoted, B is active, the switch no longer occupies the active-switch slot, and the blocked repair event remains in Redis/Asynq. The switch reaches `DONE` after repair drains if A returns. New B writes advance the old A→B version vector so delayed source writes and deletes cannot overwrite newer B state. A B→C policy can be added while old repair remains pending. When that delayed switched repair is applied to B, Worker now records a versioned event on each active outgoing bucket replication from B, so a follower added during the backlog does not miss the repaired object.
- Deletes carry explicit durable intent and source mutation versions; workers never infer deletion from missing version metadata or a missing source object. A delayed delete applies only when its exact source version is still current and newer than the target. Legacy versionless delete tasks are applied only when no vector state exists. Mutations on B during an in-progress, promoted, or done switch enqueue reverse repair until a B→A policy exists. Capturing in-progress writes also covers requests that obtained their routing context before switch completion but reach B after recovery replication starts. Recovery policies may be added while the `DONE` switch record remains, closing the former record-deletion handoff gap; keep the switch metadata until recovery replication protection exists. If an object sync event cannot be stored, Proxy returns retryable HTTP 503 instead of silently acknowledging it.
- Multipart uploads under replication are recorded in Redis with their initiating provider so routing remains correct across a switch. Markers, including successful completion receipts, remain until their bounded TTL (seven days for ordinary uploads) or explicit abort. On `NoSuchUpload`, a retry uses HEAD and matches the saved completion ETag, size, and last-modified time before returning idempotent success and re-enqueuing replication. New markers are not reconciled without a durable receipt. A crash after provider completion but before Chorus persists that receipt remains an unavoidable S3/Redis atomicity gap: Chorus fails conservatively rather than mistaking a different object at the key for this upload, so manual resolution may be needed for that narrow case.
- Each upload marker now records its own expiration. The shared user/bucket Redis set TTL is extended atomically to the latest marker deadline and never shortened by concurrent uploads; expired entries are pruned when that bucket's upload state is read or updated. A later upload in the same bucket therefore cannot extend an older completion receipt beyond its original window.
- Single-object Proxy DELETE and Worker object replication share the same destination-scoped Redis object locks. Proxy holds the relevant active, replication-target, and any completed switch's potential reverse-target locks through provider DELETE, vector advancement, and durable replication enqueue. Including that potential destination protects the handoff if B→A recovery policy is installed while the request is in flight. This closes the in-flight stale-copy race in either ordering. `DeleteObjects` batch requests use the same locks, deduplicated and sorted, across one provider batch request, per-key result interpretation, version updates, and delete-intent enqueue. Generic PUT/overwrite locking remains out of scope because Notesnook attachment keys are immutable and not reused.
- S3 `DeleteObjects` now uses those same object locks for every requested key, deduplicated and globally sorted. The lock set remains held across the single provider batch call, interpretation of per-key success/errors, successful-key version advancement, and durable replication enqueue. Normal responses use `<Deleted>` entries; quiet responses derive successful keys by excluding keyed/versioned `<Error>` entries. Failed keys do not advance version state or enqueue delete tasks. Batch deletion remains one S3 request.
- Proxy object mutations acquire a Redis-backed bucket mutation lease before policy/routing context is read. `PutObject`, `CopyObject`, `DeleteObject`, `DeleteObjects`, `CompleteMultipartUpload`, and supported object ACL/tag changes are gated; GET/HEAD/list, multipart initiation, and part upload remain ungated. The lease is recorded atomically at user and bucket scopes, uses a 30-second expiry, and renews while the request runs. A live topology lease returns retryable S3 `ServiceUnavailable`; if Redis is unavailable, mutation admission fails closed.
- Management `AddReplication`, `DeleteReplication`, `AddRouting`, `DeleteRouting`, and `DeleteSwitch` acquire an expiring topology lease before changing policy/routing state. Bucket operations gate one bucket; user-wide replication/routing gates all that user's active mutations. Active mutations produce a gRPC `Aborted` management conflict with reason `BucketHasActiveMutations` (HTTP 409 equivalent for gRPC gateways). Leases release on completion/error and expire after a process crash.
- Switch execution and promotion remain outside the topology gate. The existing zero-downtime/HA state transition must continue to route writes during an outage and cannot wait for a failed provider or an idle bucket. This pass applies the gate to operator policy/routing reconfiguration; the switch state machine continues to use its existing version-vector and repair behavior.
- Query-string SigV4 GET, PUT, and multipart UploadPart are covered by the MinIO integration test. The PUT and part requests carry the same explicit empty `Content-Type` used by the released web client; Proxy ignores that empty unsigned header after validating all headers listed in `X-Amz-SignedHeaders`, and does not forward it to storage. Non-empty unsigned `Content-Type` remains rejected. Multipart initiation/completion in the regression use the direct provider as Notesnook's internal client does.
- The default S3 backend request timeout is two hours. Notesnook's largest supported file is 5 GiB; at the sizing floor of 1 MiB/s a full-object transfer takes about 86 minutes, leaving roughly 34 minutes for provider/network overhead. Explicit per-storage `httpTimeout` values override this default and should preserve the same transfer budget.
- A completed diff check can be rerun for the same storage/bucket locations. Chorus clears the old report before enqueuing the new check; an active diff or diff-fix remains protected from replacement. If Asynq has already removed an empty completed queue, its persisted report is still treated as completed and available for rerun.

## Verification and limits

Run Go commands with Go 1.27.1 or newer. The MinIO integration test also needs .NET 8 and the AWSSDK.S3 3.7.310.8 NuGet package; it skips the SDK-specific case when `dotnet` is unavailable. Earlier passes verified standard Notesnook presigning but omitted the released client's empty `Content-Type`; the current regression covers that header on PUT and UploadPart. A released Notesnook desktop app is installed locally, but it has not been driven against the test MinIO because the available app is tied to a real API/account; the end-to-end client-binary verification remains outstanding.

In the earlier DeleteObjects/topology-gate pass, focused store, Proxy, API, and worker tests passed; its container-backed tests could not create Docker. That earlier environment result is superseded by the current pass above: Docker worked for the MinIO signing suite and isolated Compose lab, while the broad Ceph-backed `test/versioned` package remained unsuccessful.

The live Docker lab verified the blocked-event path: with A offline and a queued A-only object, switch status became `PROMOTED_WITH_BACKLOG`; Proxy and Worker restarted successfully; GET/HEAD of replicated data and new PUTs to B worked; the source-only read returned HTTP 503. The queued event remained pending and copied to B after A returned, moving the switch to `DONE`. A separate live check deleted an object on B during promoted backlog; after A returned and the reverse delete task retried, the stale object was absent from both providers. The management CLI in the lab is older than this patch and renders the new enum as `NOT_STARTED`; query `/replication/switch/get` to see `PROMOTED_WITH_BACKLOG` until `chorctl` is updated.

The final end-to-end lab run initially found a three-provider convergence failure: B→C was installed while an A→B repair event was blocked; after A returned, the delayed repair reached B but not C. A targeted Worker change now forwards that switched repair using the existing B→C version vector and event queue. A clean `test2` rerun on the rebuilt Worker reached `DONE`; direct C stat matched A/B and `chorctl diff report --brief follower:test2 follower-c:test2` reported `CONSISTENT: true`. The first rebuilt version exposed shared bucket switch metadata on B→C tasks; the final change matches metadata by exact replication ID. In that earlier lab build, the original `test` bucket's prior diff report remained stale/false and a fresh check returned InternalError despite matching direct inventories. This follow-up makes completed deterministic diff checks rerunnable; the focused MinIO-backed integration, including a second check of the same location pair, now passes. The historical live bucket was not restarted for another Compose run in this pass.

The version-vector guard covers delayed events after the newer mutation has been recorded. Single-object DELETE and DeleteObjects now serialize against Worker copies with shared per-object locks. Generic PUT/overwrite requests remain outside object locks; this is accepted for Notesnook's immutable, non-reused attachment keys. The bucket mutation lease prevents topology policy/routing changes from overlapping any visible-object write.

Asynq object events use a retry cap of `MaxInt32`, which is operationally very large but finite. Permanent provider errors such as `AccessDenied` can therefore remain in retry state; this patch does not add a permanent/transient error classifier or a separate retry subsystem.

Multipart retry recovery depends on the Redis upload marker remaining available and unexpired. Ordinary upload markers expire after seven days; an upload abandoned longer than that may not be eligible for the `NoSuchUpload` reconciliation path. S3 object mutation and Redis enqueue are not atomic for non-multipart requests; Proxy reports queue failure as retryable HTTP 503, but durable replay still depends on the client retrying.
